### Q&A-1. What an expected version means inside a 05 transaction isn't said

Quote: "Two transactions running in parallel each apply only their own changes; on the same document the last commit wins." "In 05 the applied changes keep the versioning (Q45, Q52)."
Consequence: The 05 `store(id, obj, expectedVersion)` checks the version under a lock; inside a transaction it is recorded. When is it checked: at record time, on commit, or not at all? What version does `get` return for a document stored earlier in the same transaction? The JVM 06 `Database.transaction` already records writes, applies them under a lock, checks every expected version on commit and throws `ConcurrencyException`; its `get` inside a transaction reads the stored data, not the recorded writes, the opposite of the Q52 design. A developer may copy 06 or pick last-commit-wins.
Belongs to: qa
Resolution: fixed in r9: Oskar, "I don't care if it's a or b as long as it's consistent and fullfiling the goal"; the JVM 06 transaction is the model (expected versions checked on commit).

### Quality-1. AC 2.16's "one after another" case passes with the copying design Q52 rejected

Quote: "Two transactions running in parallel each apply only their own changes; on the same document the last commit wins." AC 2.16: "WHEN two transactions store documents D1 and D2 one after another THEN the collection returns both".
Consequence: If T2 starts after T1 commits, a copy-and-copy-back `Database` passes too. Only both open and committing in turn proves "each apply only their own changes"; "last commit wins" is never checked.
Belongs to: spec
Resolution: fixed in r9: AC 2.16 has two open transactions committing in turn, and last commit wins.

### Quality-2. Parts of the transaction decision have no acceptance criterion

Quote: "`get` sees the recorded changes over the stored data"; "applies them to the storage in one step under a lock".
Consequence: No AC covers reading your own write, a recorded `delete`, or the lock (03/04 `Collection` has no locking; 05 synchronizes on its per-class map). Code that records stores but reads only live storage, or ignores `delete`, passes.
Belongs to: spec
Resolution: fixed in r9: following 06, `get` reads stored data; AC 2.16 covers delete; the lock is the storage lock, as in 06.

### Quality-3. "Keeps the versioning" for the 05 transaction doesn't say what a committed store does to the version

Quote: AC 2.9: "JVM `Database.transaction` keeps each document's stored version". "In 05 the applied changes keep the versioning".
Consequence: (a) version on applied store: +1 per store, +1 per commit, or unchanged; (b) expected version inside a transaction: checked at record time, at commit, or not offered. No AC observes it.
Belongs to: spec
Resolution: fixed in r9: version +1 per applied store; expected versions checked on commit (AC 2.16).
