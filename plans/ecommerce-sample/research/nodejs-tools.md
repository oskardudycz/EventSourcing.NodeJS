**Recommendation: `@platformatic/kafka`**, with `@confluentinc/kafka-javascript` as the fallback.

- A library author does not want a native addon in Emmett: no install-time binaries, no gap when a new Node.js major ships before prebuilt binaries. Confluent's README lists prebuilt binaries only up to Node 24, and the repo targets Node `>=24.22.1`, so the next Node major is a real risk there.
- It is pure TypeScript-friendly JS with bundled types, has transactions, manual commits, headers, and a `diagnostics_channel` design that fits OTel.
- kafkajs is out. The latest release is from 2023 and the maintainers asked for new maintainers in 2023. It still has the best OTel story, but building a new library on an unmaintained client is the wrong bet.

Risks:

- `@platformatic/kafka-opentelemetry` is young (0.x, 3 stars). If it does not cover what we need, we inject and extract `traceparent` in headers ourselves with `@opentelemetry/api` `propagation.inject/extract`. That is a small amount of code and is library-agnostic.
- Its schema registry support is marked experimental and outside semver ([README](https://github.com/platformatic/kafka)). We do not need it.
- It moves fast (minor releases often). Pin versions.
- Node `>= 22.22.0` is required. That fits the repo.

## 3. OpenTelemetry for Node

OpenTelemetry JS released SDK 3.0.0 on 2026-10-20 ([release v3.0.0](https://github.com/open-telemetry/opentelemetry-js/releases/tag/v3.0.0), 2026-11-23). Important changes:

- Minimum Node.js is `>=22.15.0`.
- `@opentelemetry/sdk-trace-base`, `sdk-trace-node` and `sdk-trace-web` are removed and replaced by `@opentelemetry/sdk-trace`. npm shows both old packages as deprecated with "Use @opentelemetry/sdk-trace package" (`npm view ... deprecated`, 2026-11-23).
- Deep imports into `build/...` no longer work. Only `exports` map paths resolve.
- `sdk-logs` is marked stable.
- Stable packages are `3.x`. Experimental packages (`sdk-node`, OTLP exporters, `instrumentation-http`) are `0.300.x`.

Context propagation through Kafka and RabbitMQ headers: the instrumentations above inject and extract W3C `traceparent` for us. Without them, the generic way is `propagation.inject(context.active(), headers)` on send and `propagation.extract(ROOT_CONTEXT, headers)` on receive, from `@opentelemetry/api` (not verified against a running test in this research).

In-process testing (the Java `opentelemetry-sdk-testing` equivalent): register a `TracerProvider` with `SimpleSpanProcessor(new InMemorySpanExporter())`, a `MeterProvider` with a reader over `InMemoryMetricExporter`, and a `LoggerProvider` with `SimpleLogRecordProcessor(new InMemoryLogRecordExporter())`. All three exporters are in the stable 3.1.1 packages (tarballs checked 2026-11-23). Emmett itself does not use these directly: its unit tests use almanac test helpers (`ObservabilitySpec`, `collectingTracer`, `testObservabilityContextGenerator`) with Vitest ([handleCommand.observability.unit.spec.ts](https://github.com/event-driven-io/emmett/blob/main/src/packages/emmett/src/commandHandling/handleCommand.observability.unit.spec.ts), [observability.int.spec.ts](https://github.com/event-driven-io/emmett/blob/main/src/packages/almanac/src/configuration/observability.int.spec.ts), 2026-11-23).

Prometheus "first sample" issue: I ran a scratch check on 2026-11-23 with `@opentelemetry/sdk-metrics@3.1.1` and `@opentelemetry/api@1.10.0` on Node 24.12.0. A counter created but never used was **not exported at all**. A counter on which we called `add(0, { outcome: 'failed' })` was exported with value `0` for that attribute set. So OTel JS behaves like the Java SDK here: to have a series from startup, call `counter.add(0, attributes)` once per attribute set at startup. A web search found no OTel JS documentation that states this ([search results included a Prometheus users thread with the same `Add(0)` workaround for Go](https://groups.google.com/g/prometheus-users/c/BBoVYf714eA)).

ESM caveat: OTel JS docs say "Much of OpenTelemetry JS documentation is written assuming the compiled application is run as CJS" and that ESM needs `--import` of the setup file plus the instrumentation hook ([doc/esm-support.md](https://github.com/open-telemetry/opentelemetry-js/blob/main/doc/esm-support.md), 2026-11-23). Emmett's Express sample starts with `tsx --import @opentelemetry/instrumentation/hook.mjs --import ./src/register.ts ./src/index.ts` ([sample package.json](https://github.com/event-driven-io/emmett/blob/main/samples/webApi/expressjs-with-postgresql/package.json), 2026-11-23).

**Recommendation:**

- Library code (later Emmett) depends only on `@opentelemetry/api` as a peer, and preferably builds on almanac rather than a second observability layer.
- The sample uses `@opentelemetry/sdk-node` 0.301.x with the three OTLP proto exporters to `grafana/otel-lgtm` on port 4318.
- Use instrumentations that do not monkey-patch where they exist: `@hono/otel` or `@fastify/otel` for the web layer. Use `instrumentation-http`, `instrumentation-pg` and `instrumentation-amqplib` where there is no alternative, loaded through the ESM hook.
- Test spans and metrics in-process with `InMemorySpanExporter`, `InMemoryMetricExporter` and `InMemoryLogRecordExporter` from the 3.x SDK packages. Call `forceFlush()` on the metric reader before reading.
- Register every counter with `add(0, attributes)` at startup.

Risks:

- SDK 3.0 is one month old. Many blog posts and examples still use `sdk-trace-base` and `sdk-trace-node`, which are now deprecated.
- Almanac's peer range on `main` is `@opentelemetry/sdk-trace >=3.0.0 <3.1.0`, but the latest is 3.1.1. Check before mixing them.
- ESM plus monkey-patching instrumentations is fragile (see the Emmett troubleshooting note in section 4).

**Recommendation: pino 10.** Add trace correlation without monkey-patching: use a pino `mixin` that reads `trace.getActiveSpan()?.spanContext()` from `@opentelemetry/api` (standard pino `mixin` option; this exact code is not verified in this research), or use almanac's logger and formatter. Risks: `instrumentation-pino` does not work under tsx with Node 24 ESM according to Emmett's sample notes. A worker-thread transport can lose the last logs on a hard crash (general pino transport behaviour, not verified here).

## 9. Contract and snapshot tests of message formats

Strictland has **no JS/TS port**. The repository [event-driven-io/strictland](https://github.com/event-driven-io/strictland) has only `src/jvm`, one branch (`main`) and only `jvm-*` release tags, the latest `jvm-0.5.0` on 2026-11-16 (`gh api`, 2026-11-23). npm has no `strictland` or `@event-driven-io/strictland` package.

What Strictland does (to port the idea): it stores the serialized JSON as `*.snap.approved.json` files in the repository, writes a `*.received.json` on mismatch, and has `thenBackwardCompatible()` and `thenForwardCompatible()` checks that compare the shared fields of two versions at every depth ([Strictland README](https://github.com/event-driven-io/strictland)).

| Vitest `toMatchInlineSnapshot`                       | same                                                                | MIT        | Writes the value into the test file. | [approvals](https://www.npmjs.com/package/approvals) | 7.3.0, 2025-04-14                                                   | Apache-2.0 | ApprovalTests for Node. `verifyAsJSON`, `.approved`/`.received` files, diff tool launch. **Recommendation: Vitest `toMatchFileSnapshot`** with one `.json` file per message type and version, so the approved file is readable JSON in pull requests and CI fails on a missing or changed contract.
