# Java e-commerce sample: inventory

This file lists what the Java sample in `EventSourcing.JVM/samples/e-commerce` contains. It is the input for the port to Node.js/TypeScript and Emmett. It describes only the Java side. It does not map anything to Node.js.

All links point to `main` of `oskardudycz/EventSourcing.JVM`. The local branch `added_strictland_contract_tests` (commit `a1e51508`) has the same tree as `origin/main` (commit `6775352a`) for `samples/e-commerce` and `.github`: `git diff origin/main HEAD` is empty. So the contract tests (`*ContractTests.java`, `testing/contracts`) and `testing/grafana/GrafanaApiTests.java` are already on `main`, and the links to them work. The only local difference is an uncommitted change to `eventcatalog/package.json` and `eventcatalog/package-lock.json` (an `overrides` block, see [EventCatalog](#55-eventcatalog)).

Line numbers point to the first line of the item (class, method or block).

The sample is one Spring Boot application with four business modules (shopping carts, orders, payments, shipments) and a `shop` package for shared page parts. The modules talk only through messages on one `MessageBus`. Each module uses Event Sourcing with a decider and an immutable entity ([README.md#L48](https://github.com/oskardudycz/EventSourcing.JVM/blob/main/samples/e-commerce/README.md#L48), [README.md#L52](https://github.com/oskardudycz/EventSourcing.JVM/blob/main/samples/e-commerce/README.md#L52)). Business-agnostic code lives in `io.eventdriven.core` ([README.md#L1049](https://github.com/oskardudycz/EventSourcing.JVM/blob/main/samples/e-commerce/README.md#L1049)).

### 2.1 Commands: `CommandHandler`

What it does: reads a stream, folds the events with `evolve` from `initial`, calls the decider (`BiFunction<Command, State, Event[]>`), and appends the new events with an expected version ([#L89](https://github.com/oskardudycz/EventSourcing.JVM/blob/main/samples/e-commerce/src/main/java/io/eventdriven/core/commands/CommandHandler.java#L89)). ### 2.3 Event store: in memory

File: [core/eventstore/inmemory/InMemoryEventStore.java#L32](https://github.com/oskardudycz/EventSourcing.JVM/blob/main/samples/e-commerce/src/main/java/io/eventdriven/core/eventstore/inmemory/InMemoryEventStore.java#L32).

- Keeps a map of streams and one global log of entries. Each entry is serialized through `MessageSerializer` (type name plus JSON bytes), so the in-memory store round-trips messages like the durable stores ([#L242](https://github.com/oskardudycz/EventSourcing.JVM/blob/main/samples/e-commerce/src/main/java/io/eventdriven/core/eventstore/inmemory/InMemoryEventStore.java#L242)).
- `append` is `synchronized`. Each event gets a new random message id and inherits correlation, causation, trace and span ids from `MessageContext.inherit()` ([#L75](https://github.com/oskardudycz/EventSourcing.JVM/blob/main/samples/e-commerce/src/main/java/io/eventdriven/core/eventstore/inmemory/InMemoryEventStore.java#L75)).
- Delivery runs after the outermost append (`dispatching` flag), entry by entry, to every subscriber behind. An event appended by a subscriber is delivered after the current one. A failing subscriber keeps its checkpoint, gets nothing more in that run, and gets the same event again on the next append. Middleware (`use`) sees each event once, before subscribers ([#L146](https://github.com/oskardudycz/EventSourcing.JVM/blob/main/samples/e-commerce/src/main/java/io/eventdriven/core/eventstore/inmemory/InMemoryEventStore.java#L146), [#L140](https://github.com/oskardudycz/EventSourcing.JVM/blob/main/samples/e-commerce/src/main/java/io/eventdriven/core/eventstore/inmemory/InMemoryEventStore.java#L140)).
- Each delivery runs inside `MessageContext.handling("handle <Type>", metadata)` ([#L176](https://github.com/oskardudycz/EventSourcing.JVM/blob/main/samples/e-commerce/src/main/java/io/eventdriven/core/eventstore/inmemory/InMemoryEventStore.java#L176)).
- Subscribers are called in subscription order ([#L169](https://github.com/oskardudycz/EventSourcing.JVM/blob/main/samples/e-commerce/src/main/java/io/eventdriven/core/eventstore/inmemory/InMemoryEventStore.java#L169)). The README relies on this order: forwarders subscribe before the saga ([README.md#L582](https://github.com/oskardudycz/EventSourcing.JVM/blob/main/samples/e-commerce/README.md#L582)).

### 2.4 Event store: KurrentDB

Files: [core/eventstore/kurrentdb/KurrentDBEventStore.java#L42](https://github.com/oskardudycz/EventSourcing.JVM/blob/main/samples/e-commerce/src/main/java/io/eventdriven/core/eventstore/kurrentdb/KurrentDBEventStore.java#L42), [core/eventstore/kurrentdb/KurrentDBSubscriptionToAll.java#L19](https://github.com/oskardudycz/EventSourcing.JVM/blob/main/samples/e-commerce/src/main/java/io/eventdriven/core/eventstore/kurrentdb/KurrentDBSubscriptionToAll.java#L19).

- Metadata keys `$correlationId`, `$causationId`, `$traceId`, `$spanId` in the event's user metadata ([#L43](https://github.com/oskardudycz/EventSourcing.JVM/blob/main/samples/e-commerce/src/main/java/io/eventdriven/core/eventstore/kurrentdb/KurrentDBEventStore.java#L43), [#L214](https://github.com/oskardudycz/EventSourcing.JVM/blob/main/samples/e-commerce/src/main/java/io/eventdriven/core/eventstore/kurrentdb/KurrentDBEventStore.java#L214)). The event id is the message id. Missing metadata falls back to the message id for correlation, and correlation for causation ([#L273](https://github.com/oskardudycz/EventSourcing.JVM/blob/main/samples/e-commerce/src/main/java/io/eventdriven/core/eventstore/kurrentdb/KurrentDBEventStore.java#L273)).
- `read` maps `StreamNotFoundException` to `StreamDoesNotExist` ([#L54](https://github.com/oskardudycz/EventSourcing.JVM/blob/main/samples/e-commerce/src/main/java/io/eventdriven/core/eventstore/kurrentdb/KurrentDBEventStore.java#L54)).
- `append` maps `ExpectedStreamVersion` to `StreamState` and `WrongExpectedVersionException` to `StreamAlreadyExists`/`Conflict` ([#L83](https://github.com/oskardudycz/EventSourcing.JVM/blob/main/samples/e-commerce/src/main/java/io/eventdriven/core/eventstore/kurrentdb/KurrentDBEventStore.java#L83), [#L233](https://github.com/oskardudycz/EventSourcing.JVM/blob/main/samples/e-commerce/src/main/java/io/eventdriven/core/eventstore/kurrentdb/KurrentDBEventStore.java#L233)). It also opens its own client span `streams.append` with `db.system=kurrentdb`, because the KurrentDB client has no spans ([#L88](https://github.com/oskardudycz/EventSourcing.JVM/blob/main/samples/e-commerce/src/main/java/io/eventdriven/core/eventstore/kurrentdb/KurrentDBEventStore.java#L88), [plans/message-broker/todo.md#L29](https://github.com/oskardudycz/EventSourcing.JVM/blob/main/samples/e-commerce/plans/message-broker/todo.md#L29)).
- `subscribe` subscribes to `$all` with a server-side filter: an event-type regular expression built from every type name the serializer knows for the subscribed classes (current, explicit, old) ([#L137](https://github.com/oskardudycz/EventSourcing.JVM/blob/main/samples/e-commerce/src/main/java/io/eventdriven/core/eventstore/kurrentdb/KurrentDBEventStore.java#L137)).
- Checkpoints are stored in the projections database (`SubscriptionCheckpoints`), not in KurrentDB. The subscription starts from the stored commit position or from the start ([#L147](https://github.com/oskardudycz/EventSourcing.JVM/blob/main/samples/e-commerce/src/main/java/io/eventdriven/core/eventstore/kurrentdb/KurrentDBEventStore.java#L147), [#L196](https://github.com/oskardudycz/EventSourcing.JVM/blob/main/samples/e-commerce/src/main/java/io/eventdriven/core/eventstore/kurrentdb/KurrentDBEventStore.java#L196)). The handler and the checkpoint save run in one transaction ([#L158](https://github.com/oskardudycz/EventSourcing.JVM/blob/main/samples/e-commerce/src/main/java/io/eventdriven/core/eventstore/kurrentdb/KurrentDBEventStore.java#L158)).
- `KurrentDBSubscriptionToAll`: on a handler failure or a cancellation it stops the subscription and resubscribes from the checkpoint after a back-off delay on a single-thread scheduler ([KurrentDBSubscriptionToAll.java#L78](https://github.com/oskardudycz/EventSourcing.JVM/blob/main/samples/e-commerce/src/main/java/io/eventdriven/core/eventstore/kurrentdb/KurrentDBSubscriptionToAll.java#L78), [#L104](https://github.com/oskardudycz/EventSourcing.JVM/blob/main/samples/e-commerce/src/main/java/io/eventdriven/core/eventstore/kurrentdb/KurrentDBSubscriptionToAll.java#L104)). A success resets the back-off. `close` waits for a running handler ([#L64](https://github.com/oskardudycz/EventSourcing.JVM/blob/main/samples/e-commerce/src/main/java/io/eventdriven/core/eventstore/kurrentdb/KurrentDBSubscriptionToAll.java#L64)).
- `whenCaughtUp` reads back the appended ranges to learn their log positions, then waits ([#L359](https://github.com/oskardudycz/EventSourcing.JVM/blob/main/samples/e-commerce/src/main/java/io/eventdriven/core/eventstore/kurrentdb/KurrentDBEventStore.java#L359)).
- Back-off: `RetryBackOff.exponential(1s)` in the application ([ECommerceApplicationConfig.java#L132](https://github.com/oskardudycz/EventSourcing.JVM/blob/main/samples/e-commerce/src/main/java/io/eventdriven/ecommerce/ECommerceApplicationConfig.java#L132)).

### 2.10 Message context: ids, causation, correlation, trace

File: [core/messaging/MessageContext.java#L15](https://github.com/oskardudycz/EventSourcing.JVM/blob/main/samples/e-commerce/src/main/java/io/eventdriven/core/messaging/MessageContext.java#L15).

- Correlation and causation ids live in Micrometer tracing baggage (`correlationId`, `causationId`); `handledMessageId` is local baggage ([#L16](https://github.com/oskardudycz/EventSourcing.JVM/blob/main/samples/e-commerce/src/main/java/io/eventdriven/core/messaging/MessageContext.java#L16), [application.properties#L53](https://github.com/oskardudycz/EventSourcing.JVM/blob/main/samples/e-commerce/src/main/resources/application.properties#L53)). Remote baggage fields travel in broker headers through Spring's observation support ([application.properties#L55](https://github.com/oskardudycz/EventSourcing.JVM/blob/main/samples/e-commerce/src/main/resources/application.properties#L55)).
- `inherit()`: new message id; correlation from baggage or a new id; causation from baggage or the correlation; trace and span ids of the current span ([#L59](https://github.com/oskardudycz/EventSourcing.JVM/blob/main/samples/e-commerce/src/main/java/io/eventdriven/core/messaging/MessageContext.java#L59)).
- `inheritForPublished(typeName, position)`: while a message is handled, the published message id is derived deterministically: `UUID.nameUUIDFromBytes("<handledMessageId>:<typeName>:<position>")`. So a redelivered handler publishes the same ids ([#L72](https://github.com/oskardudycz/EventSourcing.JVM/blob/main/samples/e-commerce/src/main/java/io/eventdriven/core/messaging/MessageContext.java#L72), [#L176](https://github.com/oskardudycz/EventSourcing.JVM/blob/main/samples/e-commerce/src/main/java/io/eventdriven/core/messaging/MessageContext.java#L176)). Appended events get random ids.
- `handling(stepName, metadata)`: opens a span `handle <Type>` parented by the message's stored trace and span ids if present, tags it with `messaging.message.id`, `messaging.message.correlation_id`, `messaging.message.causation_id`, and sets the baggage so the handled message's id becomes the causation of what follows ([#L94](https://github.com/oskardudycz/EventSourcing.JVM/blob/main/samples/e-commerce/src/main/java/io/eventdriven/core/messaging/MessageContext.java#L94), [#L157](https://github.com/oskardudycz/EventSourcing.JVM/blob/main/samples/e-commerce/src/main/java/io/eventdriven/core/messaging/MessageContext.java#L157)).
- `continuing(stepName, lastEvent)`: used by `handleContinuingTrace`; takes the correlation of the last event in the stream, so outside commands (provider webhooks, warehouse answers, worker timeouts) join the purchase's trace ([#L103](https://github.com/oskardudycz/EventSourcing.JVM/blob/main/samples/e-commerce/src/main/java/io/eventdriven/core/messaging/MessageContext.java#L103), [README.md#L822](https://github.com/oskardudycz/EventSourcing.JVM/blob/main/samples/e-commerce/README.md#L822)).
- `received(messageId, source)`: builds metadata on the consumer side from the baggage that the broker carried ([#L114](https://github.com/oskardudycz/EventSourcing.JVM/blob/main/samples/e-commerce/src/main/java/io/eventdriven/core/messaging/MessageContext.java#L114)).
- An open design decision on `continuing` is recorded in [plans/message-broker/follow-ups.md#L21](https://github.com/oskardudycz/EventSourcing.JVM/blob/main/samples/e-commerce/plans/message-broker/follow-ups.md#L21).

These ids are for diagnostics only; no business rule reads them ([README.md#L816](https://github.com/oskardudycz/EventSourcing.JVM/blob/main/samples/e-commerce/README.md#L816)).

### 2.15 HTTP: conditional reads

`ConditionalRead.newerThan(ifNoneMatch, find, whenMissing, deadline)` long-polls a view. With `If-None-Match` it waits for a version greater than the seen one, then answers 200 with a weak `ETag`, or 304 after the deadline. Without the header it waits until the document exists, else throws `whenMissing` ([core/http/ConditionalRead.java#L19](https://github.com/oskardudycz/EventSourcing.JVM/blob/main/samples/e-commerce/src/main/java/io/eventdriven/core/http/ConditionalRead.java#L19), [#L29](https://github.com/oskardudycz/EventSourcing.JVM/blob/main/samples/e-commerce/src/main/java/io/eventdriven/core/http/ConditionalRead.java#L29)). The ETag is the document version (stream position) as a weak tag ([#L45](https://github.com/oskardudycz/EventSourcing.JVM/blob/main/samples/e-commerce/src/main/java/io/eventdriven/core/http/ConditionalRead.java#L45)). Requests run on virtual threads ([application.properties#L2](https://github.com/oskardudycz/EventSourcing.JVM/blob/main/samples/e-commerce/src/main/resources/application.properties#L2)).

### 3.7 Cross-cutting business choices

- Money is `double`, rounded to whole cents ([README.md#L1061](https://github.com/oskardudycz/EventSourcing.JVM/blob/main/samples/e-commerce/README.md#L1061)).
- All handlers that receive messages are idempotent and append nothing for a message they cannot use; only the cart throws, because its commands come from a person ([README.md#L256](https://github.com/oskardudycz/EventSourcing.JVM/blob/main/samples/e-commerce/README.md#L256)).
- Payments and shipments are generic: they know a `referenceId` (a URN), never an order ([README.md#L364](https://github.com/oskardudycz/EventSourcing.JVM/blob/main/samples/e-commerce/README.md#L364)).
- Not covered: real sign-in, webhook endpoints, anonymous carts, partial reservations, returns and refunds ([README.md#L1051](https://github.com/oskardudycz/EventSourcing.JVM/blob/main/samples/e-commerce/README.md#L1051)).

## 7. Things that differ from what one might expect

- The README lists a `products` feature folder in orders ([README.md#L1044](https://github.com/oskardudycz/EventSourcing.JVM/blob/main/samples/e-commerce/README.md#L1044)), but `src/main/java/io/eventdriven/ecommerce/orders` has only `getcustomerorders`, `getorderstatus`, `pending` and `unpaid` (checked with `ls`).
- The repository's AGENTS.md names `AggregateSpecification`, but this sample has only `EventSourcedSpecification`.
- `build.gradle` configures a Mockito agent, but no test uses Mockito.
- Checkpoints of KurrentDB subscriptions live in the projections database, so the view change and the checkpoint commit together; KurrentDB's own checkpoint features are not used.
- On Kafka, a queue with a pattern other than `#` is a separate topic filled by a routing consumer, because Kafka has no topic-exchange matching.
- On RabbitMQ, only `-requests` and `-internal` channels are mandatory; responses may be dropped if nobody listens.
- Published message ids are deterministic during handling (name-based UUID), while appended event ids are random.
- No module registers an explicit or old type name yet; upcasting exists only in the core and its tests.
- The saga subscribes last on purpose, because the in-memory store delivers in subscription order and the forwarders must run first.
