### Step-2. Contract snapshots are not the form the code writes

Quote: `contractSnapshots.unit.spec.ts`: `serializedForm(contract, contract.schema.parse(data))` with `serializedForm = ... JSON.stringify({ type: contract.type, data }, null, 2)`; the data are hand-written fixtures. The broker body is `brokerBodyOf(data)` = `JSONSerializer.serialize(data)`, with the type in the `message-type` header. `orderWorkflow.ts:143` writes `shipmentId: order.shipmentId ?? null`. Spec 28.1: "GIVEN a stored event, a sent message or an HTTP body WHEN its serialized form changes THEN its snapshot test fails."
Consequence: the snapshots record a fixture passed through the documentation's Zod schema, never what the stores, the forwarders or the API produce. The real `OrderCanceled` without a reservation (`"shipmentId": null`) has no snapshot. If `?? null` is dropped and the field is omitted, no snapshot fails. Zod strips unknown keys, so a field added to an event or a read model leaves every snapshot unchanged. The "sent message" snapshots show `{type, data}`, which is not the Kafka or RabbitMQ body.
Belongs to: implementation
Resolution: Fixed. Snapshots serialize the typed examples with Emmett's `JSONSerializer` without Zod; sent messages are written as the broker form (headers from `brokerHeadersOf`, body from `brokerBodyOf`), stored ones as `{type, data}`. `OrderCanceled` required-only has `shipmentId: null`. The `OrderStatus` body now has `orderId` and `actions`, as the API writes it.
