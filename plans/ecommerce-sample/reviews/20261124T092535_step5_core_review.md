# Review: step 5, core part (Kafka and RabbitMQ)

Reviewed: the working tree for the core part of step 5 of `plan.md`: `packages/core/src/messaging/broker/`, `kafka/`, `rabbitmq/`, `testing/brokerTesting.ts`, and the changes to `messaging/index.ts` and `core/package.json`. The application wiring and Parts 3-5 are not part of this run. Earlier reviews of this step: None. Both reviewers ran on Opus.

## Step

Checked: every new file in `broker/`, `kafka/`, `rabbitmq/`, `testing/brokerTesting.ts`, the `index.ts` and `package.json` diffs; plan step 5 Parts 1-2 and step 2's group-19 list; spec groups 19-21, the Core package and Testing Decisions sections; Q5, Q22, Q24, Q32, Q33, Q37, Q45, Q55, Q57; Emmett `consumers.ts`, `subscriptionMessageSource.ts`, `messageSource.ts`, `processors.ts`, `processorStartPositions.ts`, `checkpoints.ts`, `sqliteEventStoreConsumer.ts`; Java `KafkaMessageBus`, `RabbitMQMessageBus`; every test for 20.1-20.11, 21.1-21.11 and the shared suite.

Confirmed: both consumers are Emmett `consumer` with `subscriptionMessageSource`, with factories built as in `sqliteEventStoreConsumer`. `deliveryLedger` is justified: Emmett's checkpoint is one string per processor, `Checkpointer` has only `read` and `store`, `MessageSource` has no ack or commit hook, and the chunker reads ahead. Commits and acks follow `checkpointer.store`, which runs after handling (20.5, 21.5 for reactors). 2 retries from 1 s, then `-dlt`/`-dlq` with the counter. The RabbitMQ catch-up probe matches Java.

### Step-5.1. 19.4 is not re-checked on Kafka or RabbitMQ, and the shared suite is a broker-only copy

Quote: plan step 5: "The shared forwarder and consumer suite from step 2 runs on Kafka too, which re-checks 19.1, 19.3, 19.4 and 19.5"; `brokerForwarderSuite.ts` has three tests and no 19.4 or undeclared-channel case.
Consequence: nothing tests that a broker forwarder failing after sending and before its checkpoint resends with the same ids, and the three targets can drift apart.
Belongs to: implementation
Resolution: fixed

### Step-5.2. The Kafka publish timeout doesn't bound the send

Quote: `timeout: Math.ceil(publishTimeoutInMs / attempts), requestTimeout: ..., connectTimeout: publishTimeoutInMs, retries: attempts - 1, retryDelay: 250` with `attempts = 4`; spec 20.3: "the broker doesn't acknowledge a send within the publish timeout (10 s by default) THEN the send fails".
Consequence: a send can take 10.75 s or, with connects, several times the timeout; Java bounds the whole send. The test checks only that an `Error` came, not when. The four attempts are a decision the spec doesn't make.
Belongs to: implementation
Resolution: fixed

### Step-5.3. Catch-up has no deadline and hangs the start of a processor that begins at `END`

Quote: Kafka `readLastMessageCheckpoint` loops `while (!(await hasReached(end))) await delay(25)`; RabbitMQ publishes a probe and does `await seen`; Emmett calls it before reading starts for `startFrom: 'END'`, and `whenCaughtUp`'s timeout applies only to `whenProcessed`.
Consequence: `startFrom: 'END'` makes `consumer.start()` hang forever, and `whenCaughtUp({ timeout })` on a stopped consumer blocks past its timeout. No test covers either.
Belongs to: implementation
Resolution: fixed

### Step-5.4. Processors outside the ledger let offsets be committed and acks sent before handling, or never

Quote: `checkpoints === 'DISABLED' ? inMemoryCheckpointer<...>() : ledgerCheckpointer(ledger)`, `projectorFactory: inMemoryProjector`; `lowestOf(values) => values.length === 0 ? 0n : ...`.
Consequence: a projector or a `'DISABLED'` processor doesn't hold back settling, so a reactor's checkpoint can commit a message the projector hasn't handled; a projector alone never settles; a caller's checkpointer is silently replaced; a `STOP`ped processor blocks all commits and, on RabbitMQ, stalls the queue at the prefetch limit. No test runs these branches.
Belongs to: implementation
Resolution: fixed

### Step-5.5. One failed commit or ack stops the consumer for good

Quote: `if (ready.length > 0) settling = settling.then(() => settle(ready)); return settling;`; Kafka `settle` commits with `Promise.all(... d.commit())`; RabbitMQ `channel.ack(message, true)`.
Consequence: after one rejected commit (for example during the 20.9 outage), `settling` stays rejected, every later `checkpointer.store` throws and Emmett stops the consumer; restarting the same object fails again. No test runs this path.
Belongs to: implementation
Resolution: fixed

### Step-5.6. Messages of an unknown type reach dead letters only when the caller passes `knownTypes`

Quote: `if (knownTypes !== undefined && !knownTypes.includes(type)) throw new UnreadableMessageError(...)`; `knownTypes?` is optional; spec 20.8 and 21.8.
Consequence: by default an unknown type is filtered out, checkpointed and acked: silently dropped, with no dead letter and no counter. The default path is untested.
Belongs to: implementation
Resolution: fixed

### Step-5.7. The SQLite write-lock check handed to step 5 is not done

Quote: progress.md (step 2): "On SQLite a forwarder that retries a down broker keeps the processor transaction, and with it the write lock, open. Step 5 must check this for Kafka and RabbitMQ."; the down-broker tests append nothing during the outage.
Consequence: nothing checks that a module can still append while a forwarder retries; if the lock stays open, a checkout during an outage blocks or fails with SQLITE_BUSY, against Q37's intent.
Belongs to: plan
Resolution: from the user: fix in Emmett (retry each attempt in a new transaction); the sample keeps the test as `it.fails` until Emmett releases it

### Standards-5.1. `forwardToBroker` with `BrokerPublisher` is the message bus that Q22 rejected

Quote: `export type BrokerPublisher = { publish(destination: string, message: EncodedBrokerMessage): Promise<void>; close(): Promise<void>; };`; `export const forwardToKafka = forwardToBroker;`; `export const forwardToRabbitMQ = forwardToBroker;`.
Consequence: one forwarder publishing through a bus interface with two implementations is Q22's rejected option (1); `BrokerPublisher` is a send target and `EncodedBrokerMessage` a message shape of our own, against Q57 and spec L332. Sharing pure helpers (encoding, `messageRouter`) is fair; each forwarder should send with its own broker client.
Belongs to: implementation
Resolution: fixed

### Standards-5.2. Trace context goes around Emmett's own `traceId`/`spanId` metadata

Quote: `propagation.inject(context.active(), headers)`; `decodeBrokerMessage` builds `metadata` without `traceId`/`spanId`; `withReceivedTraceContext` only in `fromBrokerQueue`.
Consequence: Emmett's processor spans never join the sender's trace; a reactor without `fromBrokerQueue` (such as `toWorkflowInbox`) loses it; the forwarder injects its own active context, not the message's.
Belongs to: implementation
Resolution: fixed

### Standards-5.3. RabbitMQ dead letters are published by hand instead of through the declared DLX

Quote: the topology declares `'x-dead-letter-exchange'` and `'x-dead-letter-strategy': 'at-least-once'`, but `rabbitMQDeadLetters` publishes to the DLX and acks the original.
Consequence: the broker's dead-lettering is never used (Java rejects without requeue), the message loses `x-death` headers, and dead-lettering depends on the publisher connection.
Belongs to: implementation
Resolution: fixed

### Standards-5.4. The catch-up wait sits in `readLastMessageCheckpoint` and has no timeout

Quote and consequence: as Step-5.3; Emmett's contract for the method is "return how far your store goes".
Belongs to: implementation
Resolution: fixed

### Standards-5.5. Tests control containers through the `docker` CLI

### Standards-5.6. The `KafkaOnAFixedPort` subclass isn't needed

## Re-review

Opus re-review of the fix round. All earlier findings are fixed or resolved as noted above.

### Re-5.1. Catch-up no longer does what spec 20.10 and 21.10 say

Quote: spec 20.10 (committed end offsets) and 21.10 (a probe per queue); plan L448 `catchUpWaitsForCommittedEndOffsets`; code `readLastMessageCheckpoint: async () => ledger.checkpointAfter(await readyCount())` with RabbitMQ `checkQueue(queue).messageCount`.
Consequence: the spec and plan describe a mechanism the code doesn't have; on RabbitMQ a ready message can be counted twice when the prefetch window is full, so `whenCaughtUp` times out. The probe avoided that race.
Belongs to: spec, plan
Resolution: fixed

### Re-5.2. Every type no processor handles goes to dead letters, and any skipped message blocks `whenCaughtUp`

Quote: `isKnownType` checks `processor.canHandle`; unreadable messages are dead-lettered and `ledger.skip(checkpoint)`; `checkpointAfter: (pending) => lastSequence + pending`.
Consequence: a `#` queue dead-letters and counts every type its module doesn't read, inflating `messaging.dead_lettered`; Java's "unknown type" means a type it can't read. After a skipped message, `whenCaughtUp` waits for another handled message or times out.
Belongs to: qa or spec (what "unknown type" means), then implementation
Resolution: fixed

### Re-5.3. On channel streams, 19.4's "append and checkpoint commit together" isn't true, and the suite hides it

Quote: spec 19.4; progress.md "a handler that throws after the append does not roll the append back in this setup"; `resendsAfterACrash: false`; `if (target.resendsAfterACrash) expect(received).toHaveLength(2);`.
Consequence: channel streams get duplicates after a forwarder crash, and the suite passes with 1 or 2 copies; the SQLite scope wraps the handler in a transaction, so the cause needs finding before the spec changes.
Belongs to: spec or qa, or implementation/Emmett if a rollback is expected
Resolution: Accepted (Claude, 2026-11-25): the duplicate comes from Emmett committing a failed handler's writes; the Emmett branch `processor_error_rolls_back` (#437) fixes it. Recheck after the upgrade.

### Re-5.4. A processor that starts at `END` holds back settling of the messages it skips

Quote: `read: ({ processorId }) => { ledger.processorStarted(processorId); return Promise.resolve({ lastCheckpoint: null }); }`; Emmett filters earlier messages before `handle`, so `checkpointer.store` never runs for them.
Consequence: nothing is acked or committed until its first handled message; on RabbitMQ a backlog of 100 skipped messages fills the prefetch window and the queue stalls for good.
Belongs to: implementation
Resolution: fixed

### Re-5.5. The Kafka send timeout is a race that leaves the real send running

Quote: `sendWithin(publishTimeoutInMs, () => producer.send(...))`; the producer has its own `timeout: publishTimeoutInMs, retries: 3`; the spec builds it with 10 s and forwards with 500 ms.
Consequence: timed-out sends keep retrying in the background, so several copies of one id arrive once the broker is back; setting the client's own timeout and retries would bound the send without a race.
Belongs to: implementation
Resolution: fixed

### Re-5.6. `package.json` lists dependencies core doesn't use as declared

Quote: `"@opentelemetry/api"` in `dependencies`; `@opentelemetry/context-async-hooks`, `core`, `sdk-trace` in `devDependencies`.
Consequence: a runtime dependency used only by unexported test code, and three unused dev dependencies left from removed code.
Belongs to: implementation
Resolution: partly fixed: see Re2-5.2


## Re-review 2

## Re-review 3

Opus. Re2-5.0 to Re2-5.6 fixed or mostly fixed. Left for when step 5 resumes (Parts 3-5):

### Re3-5.1. A failed Kafka END count stays cached and breaks every later start

Quote: `endPosition ??= pendingCount().then(...)`; reset only at the top of `subscribe`.
Consequence: one failed count at start makes every later start and `whenCaughtUp` fail until the process restarts; a count cached after `stop()` is reused on the next start.
Belongs to: implementation
Resolution: Fixed (Claude, 2026-11-25): a failed count clears `endPosition`, so the next start counts again (`kafkaConsumer.ts`). No dedicated test.

### Re3-5.2. The log start offset is used only when there is no commit, not when the commit is older than it

Quote: `(committed.get(partition) ?? -1n) >= 0n ? (committed.get(partition) ?? 0n) : (start.get(partition) ?? 0n)`
Consequence: after retention passes the commit, the count is too high and an END processor skips new messages; take the larger of the two.
Belongs to: implementation
Resolution: Fixed (Claude, 2026-11-25): the next offset is the larger of the commit and the log start offset (`kafkaConsumer.ts`). No dedicated test.

### Re3-5.3. `it.fails` turns the whole crash case into an expected failure on channel streams

Quote: `const crashCase = appendRollsBackWithTheCheckpoint ? it.fails : it;`
Consequence: on channel streams any failure passes, including a wrong id or a timeout.
Belongs to: qa
Resolution: from the coordinator: split the case: a plain test for the same ids, `it.fails` only for the single copy (#437)
Resolution status: open

### Re3-5.4. `waitForProbe` captures a signal that may already be aborted

Quote: `const stoppedSignal = activeSignal;` before the publish; then `addEventListener('abort', onStopped)`.
Consequence: a stop during the probe publish makes `whenCaughtUp` wait 30 s; check `aborted` first.
Belongs to: implementation
Resolution: Fixed (Claude, 2026-11-25): `waitForProbe` resolves at once when the signal is already aborted (`rabbitMQConsumer.ts`). No dedicated test.
