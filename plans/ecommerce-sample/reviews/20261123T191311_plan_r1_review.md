### Spec-1. Where cross-module commands land is undefined

Quote: 19.7 "a forwarder stores it in the receiving workflow's inbox"; Q44 payment/shipment workflow inputs are only worker, sandbox and capture-client commands; plan steps 8, 9.
Consequence: `AuthorizePayment`, `CapturePayment`, `CancelPayment`, `ReserveStock`, `RequestFulfillment`, `ReleaseStock` have no defined path (workflow inbox and pass-on, or a consumer on `-requests` calling the handler).
Belongs to: spec
Resolution: answered in Q48. Fixed in plan r2 (spec r6).

### Spec-2. `MESSAGING_INTERNAL_DELIVERY=broker` (default) has no meaning with `MESSAGING_BUS=in-memory`

Quote: Settings "default `broker`"; plan steps 2-9 run on SQLite and use `store`.
Consequence: Undefined whether the pair fails at start, falls back to `store`, or uses the event-store forwarder.
Belongs to: spec
Resolution: answered in Q51: the broker is emulated by streams and consumers. Fixed in plan r2 (spec r6).

### Spec-3. Group 19 holds for every target, but only step 3 lists it

Quote: 19 "These criteria hold for every forwarder target"; steps 10, 11 list only 20.x, 21.x; 19.6 summaries for payments and shipments are built in steps 8, 9.

Resolution: fixed in plan r2: steps 8, 9 cover the payment and shipment parts of 19.6 and 19.2; steps 9, 10 re-run group 19 as protection.

### Spec-5. Two Emmett changes come last, the spec says Emmett changes come first

Quote: Workspace "Emmett changes come first ... (Q36)"; steps 20 and 22 blocked by 19 and 21.
Consequence: Independent Emmett work waits behind 19 sample steps.
Belongs to: plan (or spec, if the late order is intended)
Resolution: answered in Q49: Emmett PRs in parallel, no stops. Fixed in plan r2.

### Steps-1. A failing given request now fails the test; the hook contract of a public Emmett API is left open

Quote: "today's ... stays valid" and "aFailingGivenRequestFailsTheTest"; hooks and catch-up without an options shape; `expectResponse`, `expectError`, `expectNothingAppended`, `htmlNotContaining` without tests.
Consequence: On origin/main given requests have no status check, so failing them changes behaviour for existing users. The implementer designs the public options (sender, clock and workers, published-message source, how "appended by the when step" is found, how catch-up reports new sends) alone.
Belongs to: spec (given failure), plan (options shape, missing tests)
Resolution: answered in Q50; options shape and missing tests added in plan r2.

### Steps-3. The event-store target needs a workflow only step 4 creates; "published" is undefined without a broker

Quote: step 3 "stores what it forwards in the receiving workflow's inbox"; 4.1 "asserts ... the published external event body"; 19.1 "sends it to the routing's channel with the routing's key".
Consequence: Routings map type to channel and key, not to a workflow, so a type-to-workflow mapping must be invented; what `expectPublished` observes without a broker (inbox append or a recorder) is open; whether it lists a module's own commands, as Java's does, is open.
Belongs to: plan
Resolution: fixed in plan r2: queues name the consuming workflow; a recorder observes sends, including a module's own commands.
