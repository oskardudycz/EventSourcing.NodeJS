### Q&A-1. Nothing in the spec gets the workflow's output commands onto the bus

Quote: "The workflow's output commands go to the message bus, which routes them by type." / "The core package holds the message bus with its three implementations, the forwarder, the broker consumer, the workers' loop, the in-memory consumer and the test helpers." / Q15: "the other modules' external events through a bus consumer that passes them to Emmett's `WorkflowHandler`." No answer covers outputs.
Consequence: `workflowProcessor` stores outputs in the workflow stream and hands them only to an optional `outputHandler`. Inputs from the bus go to `WorkflowHandler`, which returns `newMessages`. A developer must choose between publishing from `outputHandler` or from the bus consumer; the two give different message ids and causation (22.1, 22.2). The workflow's instance id and state are also undecided (Java `OrderSaga` is stateless; an Emmett `Workflow` needs both).
Belongs to: qa
Note: Q22 answers that `outputHandler` publishes the recorded outputs; whether through the bus or a broker-specific forwarder is still open. The workflow id and state remain.
Resolution: answered in Q22 (forwarder per broker with defined routings; the workflow's outputHandler publishes the recorded outputs), Q23 ("Order id, no state") and Q25 (inbox). To be fixed in r3.

### Q&A-2. No Emmett piece runs PostgreSQL read models on the KurrentDB and in-memory stores

Quote: "Read models are Emmett projections in PostgreSQL in every setup (Q14)." / "appends from a reactor skipping inline projections ([#432])" with no decision. / Q14.
Consequence: `pongoProjection` is a `postgreSQLProjection` that needs `context.session.connection` from the PostgreSQL consumer (emmett-postgresql pongoProjections.ts L95-117). `eventStoreDBProcessor` keeps checkpoints in KurrentDB or in memory (eventStoreDBProcessor.ts L146-147). PostgreSQL read models on KurrentDB need adapter code that is not in the core list. Where checkpoints live, and inline or async projections, are not stated.
Belongs to: qa
Note: Q19 and Q20 cover the SQLite setup (Pongo on SQLite with Emmett's SQLite consumer). The KurrentDB setup remains.
Resolution: answered in Q19/Q20 (SQLite setup) and Q26 ("Checkpoint in PostgreSQL"). To be fixed in r3.

### Q&A-5. Conditional reads in Java wait up to 1 s (long polling); the spec answers at once

Quote: 3.3: "... the response is 304." / 18.4: "(304 when nothing changed)" / 10.3: "... 503 with `Retry-After: 1`."
Consequence: Java `ConditionalRead.newerThan` waits until a newer version exists or `LongPolling.DEADLINE` (1 s) passes, and only then answers 304. Cancel, retry-payment, checkout-session and cart writes first call `LongPolling.retryIfNotFound` and only then answer 404 or 503 (OrdersController.java L104-107, ShoppingCartsController.java L105; tests ShoppingCartsApiTests.java L268, L275). Without it, tests and pages flap right after a write.
Belongs to: spec
Resolution: fixed as proposed (Q34). To be fixed in r3.

### Quality-1. No decision on how the workflow's output commands reach the bus

Quote: "The workflow's output commands go to the message bus, which routes them by type." / "a bus consumer that passes them to Emmett's `WorkflowHandler`" / "Message ids published while a message is handled are derived from the handled message's id"
Consequence: `workflowProcessor` uses the handler's result only for `stopAfter`. A developer must choose between publishing `result.messages` from the bus consumer, an `outputHandler`, or a forwarder over the workflow stream. Publishing `result.messages` loses commands on a crash between append and publish, because the redelivered input is in `processedInputIds`. The choice also decides which message the derived output ids come from.
Belongs to: qa
Note: Q22 answers that `outputHandler` publishes the recorded outputs (the shape is still open). `outputHandler` runs when the processor reads a recorded output from the store, before the checkpoint moves (workflowProcessor.ts L268-275), so a crash doesn't lose commands.
Resolution: answered in Q22 and Q25. To be fixed in r3.

### Quality-2. Version conflicts on the workflow stream: no retry rule for either input path

Quote: "Message handlers retry version conflicts (3 attempts in all)." / "the order's own events reach the workflow through a `workflowProcessor` ... external events ... through a bus consumer"
Consequence: Two sources append to one workflow stream at the same time. `WorkflowHandler` defaults to `NoRetries`, and in an Emmett processor a thrown error becomes `STOP` (processors.ts ~L662-687), so one conflict stops the order workflow processor. The spec doesn't say whether "message handlers" includes the workflow, which retry options each path passes, or what happens when retries run out.
Belongs to: qa
Resolution: rejected by Oskar: "workflowhandler is only used for synch, the rest is handled sequentially asynchronously". Q25 moves external events into the workflow inbox, so only the workflow processor handles inputs.

### Quality-3. "Fails and is retried" for the forwarder has no mechanism, and the summary read model is never decided

Quote: 23.3: "GIVEN the summary read model hasn't reached the event's stream position WHEN the forwarder handles the event THEN it fails and is retried." / "Retry and dead letters: exponential back-off ... 2 retries" (bus only)
Consequence: Emmett processors have no retry policy; a thrown error stops the processor. Who retries the forwarder, how often, and what happens after the limit is open. "Summary read model" appears only in this AC: which modules have one, what it holds (Java: `referenceId` and version) and which processor writes it are undecided. In Emmett each processor has its own checkpoint, so the summary lagging is a normal case.
Belongs to: qa
Resolution: answered in Q24: "Same handler + back-off". To be fixed in r3.

### Quality-4. PostgreSQL read models on the KurrentDB and in-memory consumers: Emmett has no processor that runs them

Quote: "Read models are Emmett projections in PostgreSQL in every setup (Q14)." / 24.1 / "In-memory consumer ... with the same processor contract as Emmett's other consumers"
Consequence: `emmett-esdb` handler context has only `{ client, messageStore }` and no projector; PostgreSQL projections need `execute`, `connection`, `transaction`. A developer must choose between a reactor writing to PostgreSQL with the checkpoint in KurrentDB (at least once, idempotent projections), a checkpoint in PostgreSQL, or something else. Inline or async is not stated; inline projections don't exist on KurrentDB, while 10.3 and 18.2 assume the read models lag.
Belongs to: qa
Note: same as Q&A-2. Q19 and Q20 cover the SQLite setup; the KurrentDB setup remains.
Resolution: answered in Q19/Q20 and Q26. To be fixed in r3.

### Quality-5. Emmett's Hono `ApiE2ESpecification` cannot be "extended" as described

Quote: "Emmett's Hono `ApiE2ESpecification`, extended with steps for HTTP requests, messages on the bus ..., time passing ... After each step it waits until the store and the bus have caught up."
Consequence: On origin/main it is a closure: steps are `TestRequest` only, `then` takes `[E2EResponseAssert]` for the `when` response, and there is no hook for consumers, buses, workers or between steps. A developer must write a new specification (wrapping Hono's, or a copy in the core), and it's unclear whether Emmett's type and signature must be kept. The catch-up rule is open: one wait each for store and bus, or repeat until both are idle (Java repeats until a round publishes nothing new).
Belongs to: qa
Resolution: answered in Q30 ("Change Emmett's first"). To be fixed in r3.

### Quality-7. The correlation id of "the purchase" doesn't match Java

Quote: 22.2: "its correlation id is the one of the purchase AND its causation id is the id of the message that caused it."
