### Q&A-1. Cancel scenarios 9.1 and 17.9 contradict Java

Quote: 9.1: "GIVEN an `Opened` order with an authorized payment and reserved stock WHEN the customer posts `cancel` THEN ... the workflow sends `CancelPayment` and `ReleaseStock`." / 17.9: "GIVEN an `Opened` order WHEN the customer cancels THEN the payment is canceled AND the stock is released."
Consequence: In Java an order with an authorized payment and reserved stock is `Confirmed` at once (OrderDecider `progress`), and cancel works only on `Opened`. Java's tests cancel an unpaid order, which sends only `ReleaseStock` (OrdersApiTests.java L90-94, PurchaseTests.java L345-348). A developer can't build the GIVEN with the ported decider, or changes the decider.
Belongs to: spec
Resolution: fixed as proposed (Q46).

### Q&A-2. A rejected fulfillment also releases the stock in Java

Quote: 7.3: "... THEN the order records `OrderShipmentFailed` and `OrderCanceled` AND the workflow sends `CancelPayment`." / 17.5 / 16.5: "GIVEN a reserved shipment WHEN `ReleaseStock` arrives THEN it records `StockReleased`."
Consequence: In Java a rejected shipment maps to `Reserved` for the saga, so `OrderCanceled` also sends `ReleaseStock`, and the shipment records `StockReleased` because `isStockHeld` includes `FulfillmentRejected` (Order.java L121-129, Shipment.java L27-31, PurchaseTests.java L268-283). As written, the stock stays held forever.
Belongs to: spec
Resolution: fixed as proposed (Q46).

### Q&A-3. The cart forwarder needs a summary too

Quote: 19.10: "GIVEN a forwarder that needs a summary (the `referenceId` of a payment or shipment) ..." / 4.1: "... with the cart id, customer id, product items, total price and time."
Consequence: Java's internal `ShoppingCartCheckedOut` has only the cart id and the time (ShoppingCartEvent.java L25). The external event takes the customer id, items and total from `ShoppingCartSummary` (ShoppingCartExternalEventForwarder L14-59). As written, a developer widens the internal event (changing the stored contract) or reads the cart stream.
Belongs to: spec
Resolution: fixed as proposed (Q46).

### Q&A-4. "Almanac's Pino provider" is a tracer, and Q33 didn't pick it

Quote: "Logs go through Almanac's Pino provider (Q33)." / Q33: "I don't care about pino unless we really have some logs, but we can use it".
Consequence: Almanac's `pinoTracer(pino): Tracer` writes spans as pino lines with an empty trace id; it is not a log channel. Almanac's OTel provider already exports logs with trace and span ids (otel.int.spec.ts). `instrumentation-pino` doesn't work under tsx + Node 24 ESM. A developer must choose between `pinoTracer` (loses OTLP traces), two tracers, or plain pino whose logs don't reach Grafana.
Belongs to: qa
Resolution: answered in Q41: plain pino.

### Q&A-5. Only forwarders retry; the workflow's `outputHandler` and the other processors stop on the first failure

Quote: "On any failure the processor retries the batch with exponential back-off, without a limit (Q24)." / "The workflow processor's `outputHandler` sends the recorded output commands to the broker (Q22)."
Consequence: In Emmett a thrown error becomes `STOP` (processors.ts L662-689), and `workflowProcessor` stops on an `EmmettError` from `outputHandler`. With the broker down, the order workflow stops until a restart, and so do the KurrentDB read-model processor and the gateway-client reactors. Java runs every subscription with `RetryBackOff.exponential`.
Belongs to: qa
Resolution: answered in Q37: retry in handlers and a processor retry policy in Emmett.

### Q&A-6. Inline or async projections on SQLite and PostgreSQL is undecided, and #432 has no decision

Quote: "Read models are Pongo projections (Q20) ..." / Further Notes: "appends from a reactor skipping inline projections ([#432])" / 3.5, 10.3, 18.2 assume the read model lags.
Consequence: Inline gives no lag (3.5, 10.3 can't happen) and hits #432 for appends from processors; async lags and needs a checkpoint rule. Q26 settled only KurrentDB.
Belongs to: qa
Resolution: answered in Q38: inline.

### Q&A-7. How the capture client sends `FailPaymentCapture` is not covered

Belongs to: qa
Resolution: answered in Q40 and Q44: payment and shipment workflows, delivery by store consumer or broker.

### Q&A-8. The settings make three fixed pairs out of two independent variables; connection settings have no names

Quote: 25.1: "GIVEN `MESSAGING_BUS=rabbitmq` and `EVENTSTORE_TYPE=postgresql` ... `kafka` with `kurrentdb`, and `in-memory` with `sqlite`." / Settings list.

Belongs to: qa (combinations), spec (connection names)

## Quality

Checked: spec r3 in full; qa.md Q1-Q34; the r2 review and resolutions. Emmett origin/main: workflowProcessor.ts, handleWorkflow.ts, processors.ts, consumers.ts, emmett-esdb eventStoreDBProcessor.ts and consumer, emmett-sqlite sqliteProcessor.ts and consumer, Pongo projection files, PostgreSQL workflow consumer int spec, appendToStream correlation metadata. Java: CaptureGatewayClient, PricedProductItem and ProductItems rounding, OrderCanceled, payments folders.

Feasibility summary: the workflow processor with the inbox mode and `outputHandler` works (workflowProcessor.ts L224-283), with the gaps in Quality-2, 3, 4 and 10. KurrentDB read models with the checkpoint in PostgreSQL have no wall, but nothing in Emmett does it: the core builds a processor on `reactor` with a PostgreSQL `processingScope` and checkpointer, which stores the checkpoint in the same scope as the batch (processors.ts L1024-1110). Pongo on SQLite with a temporary file is supported; the wall is Quality-6. Forwarder retry has no mechanism (Quality-1).

### Quality-1. "Retries the batch with back-off, without a limit" has no mechanism in Emmett

Quote: "On any failure the processor retries the batch with exponential back-off, without a limit (Q24)." / 19.3, 19.7, 19.11.
Consequence: An error in a handler becomes `STOP`, and the processor doesn't run again until a restart (processors.ts L662-690, L1150-1155). The consumer gives each batch to all its processors and waits for all (consumers.ts L455). Options: (a) a retry loop inside the forwarder, which blocks every processor on that consumer while the broker is down (read models, workflow, other forwarders); (b) one consumer per forwarder; (c) restart the stopped processor from outside. Each gives a different 19.11 and catch-up (21.1).
Belongs to: qa
Resolution: answered in Q37.

### Quality-2. Nothing says what the workflow's `outputHandler` does when the broker is down or a routing is missing

Quote: "the workflow processor's `outputHandler` sends each recorded output command to the broker ... before the checkpoint moves" / 19.3, 19.11 cover only "the forwarder".
Consequence: An `outputHandler` that throws or returns an `EmmettError` stops the order workflow processor for good (workflowProcessor.ts L268-283), freezing every order. Stop, retry like forwarders, or something else is open.
Belongs to: qa
Resolution: answered in Q37.

### Quality-3. How the consumer "appends to the inbox" is open

Quote: "A consumer of the orders module's response queues appends each external event to the workflow's inbox stream (with `NO_CONCURRENCY_CHECK`) and does nothing else."
Consequence: The inbox entry must have type `<WorkflowName>:<type>` and metadata `{input: true, originalMessageId, action}` (handleWorkflow.ts L340-385); an entry without the prefix gets copied again (L171, L351). Options: (a) call `WorkflowHandler` with the inbox mode (its store-only path), though Q25 calls `WorkflowHandler` the synchronous path; (b) write the prefixed entry by hand; (c) append the plain event and let the processor copy it. Each stores something different (28.1, 19.8).
Belongs to: qa
Resolution: answered in Q45.

### Quality-4. In the inbox mode, Emmett's input dedup doesn't apply, so a replay sends workflow outputs again with new ids

Quote: 19.8: "... it sends the same messages again with the same message ids." / 5.2 / "a crash doesn't lose a command".
Consequence: For a prefixed inbox entry, Emmett checks `processedInputIds.has(inputMessageId)` with the copy's own store id, while `processedInputIds` holds `originalMessageId` values (handleWorkflow.ts L253-256, L165-168, L445-450). A broker redelivery or a crash after the output append and before the checkpoint decides the input again, and new outputs with new ids reach the broker. 5.2 still passes because the order decider drops a second `PlaceOrder`. Accept duplicates and leave them to the deciders, or prevent them?
Belongs to: qa
Resolution: answered in Q43: filed as emmett#434; handlers are idempotent.

### Quality-5. Inline or async read models on PostgreSQL and SQLite is still open

Quote: "Read models are Pongo projections (Q20) ..." / 3.5, 10.3.
Consequence: Same as Q&A-6.
Belongs to: spec
Resolution: answered in Q38: inline.

### Quality-6. SQLite setup: the in-memory forwarder delivers inside the processor's write transaction

Quote: "the in-memory forwarder delivers each message at once to the handlers of each matching queue" / 19.10 / "the store, its consumer and Pongo open more than one connection."
Consequence: The emmett-sqlite processor wraps each batch in `pool.withTransaction` (sqliteProcessor.ts L231), so after the summary write it holds the file's write lock. Handlers called at once append on another connection and wait until the busy timeout; the forwarder fails and retries without a limit, and the setup stalls. Options: pass the processor's `session.messageStore` to the handlers, deliver after the commit, or drop the summary write from that handler. Not run; from the transaction scope.
Belongs to: qa
Resolution: rejected: not verified, and "after commit is not acceptable" (Q47). Forwarders don't run other modules' handlers.

### Quality-7. Settings: mixed values and connection settings are undefined

Quote: "`MESSAGING_BUS` ... default `kafka`, `EVENTSTORE_TYPE` ... default `kurrentdb`" / 25.1 / 25.2.
Consequence: Same as Q&A-8. `EVENTSTORE_TYPE=sqlite` alone gives Kafka + SQLite through the default. Docker Compose and CI must match the connection names.
Belongs to: qa
Resolution: answered in Q42 and Q46.

### Quality-8. The money scenario passes without rounding and has no values

Quote: 26.1: "GIVEN products with prices in whole cents WHEN a cart totals them THEN the total is rounded to whole cents."
Consequence: Java keeps a `double` in currency units and rounds with `Math.round(x * 100) / 100.0` (PricedProductItem.java L19, ProductItems.java L67). Read as integer cents, the test passes with no rounding. No example (such as 3 × 19.99 = 59.97).
Belongs to: spec
Resolution: fixed as proposed (Q46).

Consequence: Same as Q&A-7.

### Quality-10. Every order event costs an extra store write in the inbox mode

Quote: "The workflow processor handles the order's own events and the inbox inputs, one after another." / Q25 talks only of external events.
Consequence: With `separateInputInboxFromProcessing`, an input without the prefix, such as `orders.OrderPlaced` from the order stream, is first copied into the workflow stream and decided when the processor reads the copy (handleWorkflow.ts L351-385). One extra append and pass per order event (`OrderPlaced`, `OrderConfirmed`, `OrderPaymentDue`, `OrderPaymentRetried`, `OrderCanceled`). No answer allows it.
Belongs to: qa
Resolution: accepted: "use inbox mode for now" (Q47).

(default `10s`)" / "Commands that come from the broker carry `now` set by the facade that receives them".
Consequence: Nothing checks the same-transaction checkpoint, the `outputHandler` crash path, the RabbitMQ publish timeout (19.7 covers only Kafka) or who sets `now`.
