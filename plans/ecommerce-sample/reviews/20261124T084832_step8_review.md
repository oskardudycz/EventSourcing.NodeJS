### Step-8.1. A workflow processor's `retry` option now also becomes the processor retry policy

Quote: `BaseMessageProcessorOptions` gets `retry?: AsyncRetryOptions`, used as `asyncRetry(() => ... options.eachMessage(...), options.retry)`. Unchanged `workflowProcessor.ts` has `retry?: WorkflowHandlerRetryOptions` and `return reactor({ ...rest, ... })`.
Consequence: every existing `workflowProcessor({ retry: { onVersionConflict: true } })` now also retries the whole processor with async-retry's defaults (10 retries, about 17 minutes) and retries real conflicts on two levels. The step asks for an optional policy that keeps today's default. No test covers a workflow processor with `retry`.
Belongs to: implementation
Resolution: fixed

### Step-8.2. A `CommandHandler` with an array `commandType` registers series at 0 that its commands never increase

Quote: `registerCommandTypes` adds 0 per `{status, type}` of `options.commandType`; the counter is incremented with `...(typeof context.commandType === 'string' ? { [A.command.type]: context.commandType } : {})`. The test uses `commandType: commandTypes` (an array) with `.when(() => undefined)`.
Consequence: failures of such a handler land in a series without a type label, so the per-type failure series stay at 0 and `increase()` still misses the first failure, which is what #433 and Q35 fix.
Belongs to: implementation
Resolution: fixed

### Step-8.3. `DeciderCommandHandler` registers the zero series again on every command

Quote: `DeciderCommandHandler = (options) => { registerKnownCommandTypes(options); return deciderCommandHandlerFor(options); }`; inside, each call runs `await CommandHandler<...>({ ...rest, ... })(...)`, which registers again.
Consequence: 2 × N extra `add(0)` per decider command, work added to every run that the step does not allow ("when a handler or store is set up"). After one command, `recordedValues` is `[0,0,0,0,0,0,0,0,1]`, not `[0,0,0,0,1]`.
Belongs to: implementation
Resolution: fixed

### Step-8.4. The metric tests check less than "covers success and failure series at 0"

Quote: `.recordedValues([0, 0, 0, 0]).hasAttributes({ type: 'AddItem', status: 'success' })` (`hasAttributes` checks only the first entry); `countsACommandThatFailsInTheSeriesCreatedAtZero` uses `.recordedValues([0, 0, 1])` with no attribute check.
Consequence: no test shows that a `failure` series is created at 0, or that the first failure or append lands in the series created at 0; Step-8.2 would pass every test.
Belongs to: implementation
Resolution: fixed (after Oskar's decisions: #433 per-processor event types, processorRetry)

### Step-8.5. New public APIs for the known types that the step leaves open

Quote: `EventStoreObservabilityConfig` gets `eventTypes?: readonly string[]`; the reading counter is also registered at 0; `registerKnownCommandTypes` is exported through `commandHandling/index.ts`. Issue #433: "create the appended-events series at `0` for each event type that a processor handles, when it starts".
Consequence: a store-level option on every event store, an extra reading series and an exported helper all become public API to keep; #433 proposed per-processor event types instead, and neither the step nor the spec chooses.
Belongs to: plan
Resolution: fixed (after Oskar's decisions: #433 per-processor event types, processorRetry)

### Step-8.6. With the `fetch` option, appended-event checks run on a store the application never uses

Quote: with `fetch`, `const eventStore = WrapEventStore(getEventStore?.() ?? getInMemoryEventStore())` is a wrapper the application never gets; `expectNoNewEvents = () => ({ check: ({ appended }) => assertEqual(0, appended.length, ...) })`. The core rejects this case: `'Checking appended events needs the getEventStore option'`, guarded by `checkingAppendedEventsWithoutAnEventStoreFailsNamingTheOption`.
Consequence: `expectNoNewEvents()` always passes, `expectNewEvents(...)` always fails with a confusing message, and a given `existingStream(...)` goes to a store the application can't read. The port drops the core's behaviour and its test, though the step asks for "the step-1 helper tests, ported".
Belongs to: implementation
Resolution: fixed

### Step-8.7. The appended-event expectations don't match the core or the spec in names or strictness

Quote: spec.md L379: "`expectAppended`, `expectNothingAppended`". The core checks stream names and counts, then `assertMatches`. The branch has `if (expectedStreams.length > 0) assertMatches(outcome.appended, expectedStreams);`, `expectNoNewEvents`, `expectNewEvents`, and renames `send` to `sendMessages`.
Consequence: when the sample switches to Emmett's version (Q49), it has to rename steps and expectations, and its checks get weaker: extra events or streams pass, and the order of streams matters. The step asks both for "the shape the sample's core built in step 1" and "as #436 proposes", and doesn't say which wins.
Belongs to: plan
Resolution: from the user: Emmett names, core strictness; fixed

### Step-8.8. The ported expectation tests check less than the core's, and one error path has no test

Quote: the test `fails when the when step published nothing but something was expected` runs `expectNothingPublished()` on a step that published; `expectPublishedFailsWhenMessagesDifferOrAreOutOfOrder` and `redirectsToFailsWhenThereIsNoLocation` were not ported; `throw new EmmettError('The response has no Location header')` is never run.
Consequence: a subset or order-blind `expectPublished` would pass every test, and the "no Location" path is untested.
Belongs to: implementation
Resolution: fixed

### Step-8.9. `getApplication` now gets a spread copy of the store

Quote: `const eventStore = WrapEventStore(optionsOrGetEventStore.getEventStore()); return specificationFor(optionsOrGetEventStore.getApplication(eventStore), eventStore)`; `wrapEventStore` returns `{ ...eventStore, ... }`.
Consequence: for a class-based store such as `MongoDBEventStoreImplementation`, prototype methods such as `streamExists` are lost, so an existing E2E test that uses them, or relies on store identity, breaks. No test covers a class-based store.
Belongs to: implementation
Resolution: fixed

### Step-8.10. The Hono docs describe the old limits

Quote: `src/docs/frameworks/honojs.md` L250: "sends the given requests in order, sends the request under test, and checks the final response"; L269: "`ApiE2ESpecification.then` accepts one response assertion in a one-element array". Issue #436 cites the docs as part of the problem.
Consequence: once released, the docs say the new API can't do what it does. The step doesn't mention docs.
Belongs to: plan
Resolution: from the user: yes, same branch; fixed

## Re-review 2

Reviewed 23ab01ef (metrics) and 0a09ce3c (retry in a new processing scope per attempt), Opus. Step-8.4, Step-8.5, Standards-8.6, Re-8.1 and Re-8.3 are fixed. Without a policy the processor behaves exactly as on `main`.

### Re2-8.1. `close()` does not stop a retry that is waiting, and later attempts run without the lock

Quote: `close` sets `isActive = false` and releases the lock; `asyncRetry(() => Promise.resolve(processingScope(...)), options.retry)` never checks `isActive` between attempts.
Consequence: after a close during back-off, the message keeps being retried for the whole policy without the processor lock, so a second instance can handle it at the same time, and the consumer's close waits.
Belongs to: implementation
Resolution: fixed (aaa20ca1)

### Re2-8.2. A commit that fails after the checkpoint is stored makes the retry skip the message

Quote: inside the retried scope: `if (storeCheckpointResult.success) { lastCheckpoint = storeCheckpointResult.newCheckpoint; ... }`; the commit runs after the callback; the next attempt filters on `!wasMessageHandled(message, lastCheckpoint)`.
Consequence: when the COMMIT fails, the in-memory checkpoint has already moved, so the retry handles nothing and reports success: the message's effects are lost silently.
Belongs to: implementation
Resolution: fixed (aaa20ca1)

### Re2-8.3. Every retried attempt logs "Processor stopped" at error level

Quote: `catch (err) { messageScope.log(messageHandlingFailed(message, err)); throw err; }` with `'Processor stopped: message handling failed'`, now once per attempt.
Consequence: a recovered failure produces error logs saying the processor stopped, and alerts on them fire.
Belongs to: implementation
Resolution: fixed (aaa20ca1)

### Re2-8.4. With any retry policy, a batch is committed one message at a time, even when nothing fails

Quote: `if (options.retry && !isCustomBatch && messages.length > 1) { for (const message of messages) { ... processor.handle([message], partialContext) ... } }`
Consequence: 100 commits and checkpoint writes per 100-message batch on the happy path, also for `retry: NoRetries`.
Belongs to: plan
Resolution: from the user via Q61 item 6: one scope per handled message with a policy; fixed (6c750a8a, 8296b9b0)
