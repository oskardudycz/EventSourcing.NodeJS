# Porting the Java e-commerce sample to Node.js on Emmett

Status: research for discussion. Nothing below is implemented, and no decision is made.

Date: 2026-11-23. Baselines: the Java sample on `EventSourcing.JVM` `main` (commit `6775352a`), Emmett `origin/main` 0.43.0-rc.3 (commit `0b9b5c7b`), and the npm registry on the same date.

## Research files

Each file has the full findings, and every claim links to a source line, an issue or a package page.

- [research/java-sample-inventory.md](research/java-sample-inventory.md): what the Java sample has. It covers the core building blocks, the four modules, the channels and routes, the tests, and the tooling.
- [research/emmett-inventory.md](research/emmett-inventory.md): what Emmett `main` has, package by package, the work in progress that is not on `main`, and the [gaps for this port](research/emmett-inventory.md#gaps-for-an-e-commerce-port).
- [research/nodejs-tools.md](research/nodejs-tools.md): Node.js tools for each piece that Emmett doesn't cover, with versions, maintenance, licenses and risks, and a [summary table](research/nodejs-tools.md#summary-of-recommendations).

## Short answer

Emmett already covers the inside of each module. That means the deciders, command handling with optimistic concurrency and retries, the PostgreSQL, KurrentDB (via the EventStoreDB client), MongoDB and SQLite event stores, consumers with checkpoints, Pongo and SQL read models, message versioning with `schemaVersion`, workflows, the Express and Hono web helpers, and observability through Almanac.

Emmett does not cover the space between modules. There is nothing for Kafka, RabbitMQ or any other broker. There is no forwarder or outbox, no inbound broker consumer, no durable timeouts, and no routing of workflow outputs to other modules. Its `ApiE2ESpecification` takes only HTTP steps. That space is most of what the Java sample teaches, so it is the core code we write in the sample first and later move to Emmett.

## Core code to write in the sample, and its way to Emmett

The list is ordered by what the modules need first. Each item names the Emmett issue or RFC section it relates to, so the later PR has a home.

1. **Message bus with routes**: a publish and subscribe contract with channels, queues bound with topic patterns, and routing keys. It has in-memory, Kafka and RabbitMQ implementations, and headers for the message type, `schemaVersion`, ids, correlation, causation and `traceparent`. Emmett relation: workflow RFC "Messaging System Support" (local `src/rfc/001-Workflow.md`, not on `main`). No issue exists yet.
2. **Forwarder processor**: a processor type on Emmett's `consumer()` that maps internal events to external ones and publishes them, with derived ids for deduplication. Emmett relation: none on `main` ([Emmett §3](research/emmett-inventory.md#forwarder-outbox-brokers)). No issue exists yet.
3. **Inbound broker consumer**: subscribes to a queue and calls a handler, with retries and a dead-letter path. Emmett relation: the RFC "Error Handling Evolution" section.
4. **Deadline workers**: an interval loop over a to-do list projection. Emmett relation: the RFC "Scheduled Message Support" section.
5. **Workflow outputs to the bus**: routes a workflow's commands to other modules. Emmett relation: the RFC "Other Workflow Patterns" section (a saga as a stateless router).
6. **Telemetry**: broker span propagation, the processor kind attribute (project, forward, react), and counters at 0. Emmett relation: [#433](https://github.com/event-driven-io/emmett/issues/433), [#345](https://github.com/event-driven-io/emmett/issues/345), the remote `otel_instrumentation` and `observability` branches (content not checked).
7. **`ApiE2ESpecification` steps and expectations**: message steps, time steps, `expectPublished`, `expectTrace`, `expectCausation`, `expectMetric`. Emmett relation: none yet.
8. **Test containers**: Kafka, RabbitMQ, otel-lgtm. Emmett relation: `emmett-testcontainers` and [#384](https://github.com/event-driven-io/emmett/issues/384).

Work that is already under way in Emmett and that the sample needs: the in-memory `consumer()` ([#427](https://github.com/event-driven-io/emmett/issues/427), your `in_memory_consumer` branch), and appends from a reactor running inline projections ([#432](https://github.com/event-driven-io/emmett/issues/432)).

## Things to know before starting

- The Node.js samples use Node 24.22.1 (`.nvmrc`). The OTel SDK 3.x needs Node >= 22.15, and `@confluentinc/kafka-javascript` lists prebuilt binaries only up to Node 24 ([tools §1](research/nodejs-tools.md#1-kafka-client), [§3](research/nodejs-tools.md#3-opentelemetry-for-node)).
- The Java saga must subscribe last, because event order depends on the order of the subscriptions ([Java §3.1](research/java-sample-inventory.md#31-channels-queues-and-routes-whole-application)). With Emmett's `consumer()`, each processor keeps its own checkpoint, so the port must not rely on that order.
- The Emmett and Pongo npm packages have an empty license field. That is not verified further ([tools](research/nodejs-tools.md)).
- Drift that the Java inventory found in the Java sample, to fix there, not in the port: the README lists an orders `products` folder that doesn't exist, `build.gradle` sets up a Mockito agent that no test uses, and the `plans` folder still says `samples/distributed-processes` ([Java §7](research/java-sample-inventory.md#7-things-that-differ-from-what-one-might-expect)).

Two differences to handle:

- Emmett's metric names differ from the Java sample's. Emmett uses names such as `emmett.command.handling.duration` and `emmett.processor.processing.duration` ([Emmett §9](research/emmett-inventory.md#9-observability)), and the Java sample uses `eventdriven.command.*` ([Java §2.1](research/java-sample-inventory.md#21-commands-commandhandler)). The dashboards and alerts must use Emmett's names, or the sample adds its own counters.
- Emmett creates its metric series on the first value, so the dashboards miss the first failure of each type ([#433](https://github.com/event-driven-io/emmett/issues/433)). The Java sample hit the same issue in `OtlpExportTests`.

## Decisions

Oskar's answers on 2026-11-23:

1. Folder: `samples/e-commerce`, as in the Java repository.
2. Web framework: Hono, with `hono/jsx` for the htmx pages.
3. Setups: the same three as in Java: in memory; Kafka + KurrentDB; RabbitMQ + PostgreSQL.
4. Order process: an Emmett `Workflow`.
5. Core code: the sample writes its own consumers, bus and forwarders first, as npm workspace packages inside `samples/e-commerce`. The business-agnostic core goes into packages shaped like future Emmett packages, and the shop stays one app package. The packages move to Emmett afterwards.
6. Contract tests: Vitest file snapshots first. Strictland gets a Node.js port later.
7. Scope: everything, including the htmx pages, OpenAPI, AsyncAPI and EventCatalog.
8. The Node.js repository has no combined distributed-processes sample, so there is nothing to split. `hotelManagement` stays as it is.
9. Kafka client: `@platformatic/kafka`. Confluent's 1.11.0 release ships prebuilt binaries only up to Node 24 (ABI 137), none for Node 26 ([release assets](https://github.com/confluentinc/confluent-kafka-javascript/releases/tag/v1.11.0), checked 2026-11-23), and kafkajs had its last release in February 2023 ([tools §1](research/nodejs-tools.md#1-kafka-client)).
10. Telemetry tests come after the modules and the process work. They need `ApiE2ESpecification` extended with `expectTrace`, `expectCausation` and `expectMetric`. The message and time steps come first, because module tests set up through the messages they receive.
